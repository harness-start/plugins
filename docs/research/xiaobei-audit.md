# xiaobei 审计结论

## 结论先说

这次不新增插件。

xiaobei 的长处是把内容生产、平台发布、数据回收、客户跟进和运维脚本装进同一个业务系统。这个思路在它自己的 OpenClaw、账号、浏览器、定时任务和 SQLite 环境里能工作，但拆到本仓库后，大部分环节既没有完整运行依赖，也没有 Hook 能稳定观察的事件。把其中一个环节单独包装成插件，只会得到一个名字完整、效果残缺的空壳。

本次只吸收一件能说清因果关系的事：视频抽帧后检测近黑画面，并让现有独立审查明确确认这些画面是否符合预期。它属于 `video-production` 已有的 probe → review → release 闭环，不需要新插件，也不需要新 Hook。

## 看到的事实

### 业务结构

xiaobei 不是一组彼此独立的 Skill，而是一套强绑定运行环境的业务应用：

- crew workspace 决定角色、权限和可用 Skill；
- 平台 Skill 依赖登录态、浏览器、固定 IP、中转服务或平台接口；
- 内容校准依赖发布前预测、发布记录、定时取数、SQLite 数据和后续复盘共同存在；
- 视频生产依赖 FFmpeg、素材下载、TTS、外部生成模型和项目目录约定；
- 安装脚本负责 OpenClaw、daemon、workspace、软链接和系统服务，而不是可独立发布的插件运行时。

静态扫描也能看到这种耦合：365 个审计项中，124 个出现网络访问，87 个出现浏览器自动化信号，61 个涉及数据库，105 个涉及凭据，15 个涉及服务状态修改，26 个包含破坏性文件操作信号。275 个非测试脚本中，只有 29 个找到了直接相邻的测试证据。

### 内容校准并不适合拆成插件

`content-calibrator` 单独看有盲预测、评分、阈值和复盘，但实际闭环还依赖 `published-track`、各平台发布器、定时取数、工作区文件和 agent 遵守“先预测、后看数据”的文字纪律。当前仓库无法从宿主事件证明这些步骤真实发生，也无法在干净消费者环境中提供平台数据。

所以不实现 `content-calibration`，也不换个名字继续包装。内容生产 → 发布 → 指标回流 → 复盘只有在完整业务产品里才成立；缺一段就不应声称形成闭环。

### 中央编排不适合搬过来

`complex-task` 要求主 agent 只做管理、每个子任务都配执行者和评估者，并把项目状态长期落盘。这会把简单任务也推成固定仪式，而且与本仓库“使用宿主原生 agent、父 agent 对最终证据负责”的边界冲突。

因此不实现 crew 编排、外部 Skill 供应链或长期任务账本门禁。现有 `execution-discipline`、测试、产物 writer 和宿主协作能力已经覆盖需要机械保证的部分。

### 平台自动化不是通用插件

发布、互动、获客、客服和账号管理脚本依赖具体平台页面、账号状态、Cookie、IP、第三方服务和平台规则。Hook 能看到一条命令，不等于能证明内容发布成功、指标真实或互动合规。它们适合作为完整产品的连接器，不适合作为本仓库的通用插件。

### 已有能力不重复造轮子

- 视频生产与审查归 `video-production`；
- 调研、来源和证据归 `evidence-based-research`；
- PPT、视觉页面和海报分别归 `presentation-production`、`interface-craft`、`poster-production`；
- Python、Shell、工程方法和命令风险已有对应工程插件。

这些条目只作为对照，不创建重名或更上层的治理插件。

## 本次吸收的改进

xiaobei 的视频审查会抽取多个位置的画面并尝试识别黑帧。它的实现存在亮度解析和占位值混用的问题，不能直接采用；但“抽帧后把可疑黑画面交给审查者确认”本身合理。

本仓的实现边界是：

- 在 `video-production` 已有采样帧上读取 FFmpeg `signalstats` 的 `YAVG` 和 `YMAX`；
- `YAVG <= 20` 且 `YMAX <= 32` 时标记为 `blackCandidate`；
- probe 只记录事实，不直接失败，因为黑屏可能是有意转场或剧情画面；
- review 必须逐个把候选标为 `expected` 或 `unexpected`；
- 缺少确认或存在 `unexpected` 时拒绝生成通过的 review，release 继续依赖现有新鲜度和摘要绑定。

这条改进有完整因果链：解码帧 → 记录亮度 → 找出候选 → 独立审查确认 → release 验证当前审查证据。它没有扩大 Hook 职责，也没有引入外部服务。

## 可证伪假设

- 亮度阈值只用于召回候选，不代表画面质量结论；如果真实素材产生大量无意义候选，应调整阈值或采样策略，而不是自动放行。
- 当前 start/mid/end 与 shot review frame 的采样能覆盖最常见的意外黑帧；它不能证明未采样帧不存在短暂黑屏。
- 静态依赖和副作用是审计信号，不是运行时执行证明；需要采用某个具体能力时，仍应单独做动态验证。
