# Reference analysis

Use this when the user supplies screenshots, a public page, brand assets, or an existing render. Inspect local project evidence first. Remote references inform direction but do not override project-owned assets or licenses.

## Extract evidence

Separate the result into:

- **Facts** — visible or inspectable properties with a source anchor: composition, hierarchy, palette roles, type behavior, spacing rhythm, surface strategy, imagery role, responsive behavior, and motion state changes.
- **Inferences** — explanations supported by those facts, such as why a focal element leads or why a surface reads as dense.
- **Assumptions** — falsifiable claims with a verification path. A screenshot does not prove an exact font, token value, breakpoint, animation curve, or component library.

Translate references into project decisions, not imitation. Preserve the product's own logo, vocabulary, content, and interaction model. Do not copy proprietary assets, signature layouts, or named-brand values merely because they are visible.

When image generation is available in the host, it may produce a direction board or project-bound mockup after the evidence pass. This is optional: published behavior must still work in a clean consumer environment without an image tool. Record any generated image as a reference, not as proof that the implementation matches it.

Feed durable findings into the Evidence and Direction sections of [Design memory](design-memory.md). Keep temporary inspiration and rejected directions out of the project contract.
